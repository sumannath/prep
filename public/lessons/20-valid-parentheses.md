# Valid Parentheses (LeetCode 20) — Complete Interview Lesson

## 1. Problem, restated in your own words

> Given a string of **only six possible characters** — the three openers `(`, `[`, `{` and their three closers `)`, `]`, `}` — decide whether it is **properly nested**: every closer must match the type of, and appear in the right position relative to, the opener it closes. Return `true` or `false`.

Equivalently, `s` is valid iff it belongs to the language generated by:

```
S → ( S ) | [ S ] | { S } | ε
```

The three concrete ways a string can be **invalid**:

1. A closer arrives when **nothing is open** (e.g. `")("`).
2. A closer arrives but the **most recent unclosed opener is a different type** (e.g. `"(]"`, `"([)]"`).
3. The string ends with **openers never closed** (e.g. `"(("`).

The interviewer is really testing: can you recognize that *order of resolution* is a **Last-In-First-Out** relationship, and translate that into a stack without fumbling edge cases.

---

## 2. Decoding the constraints

| Constraint | What it tells you |
|---|---|
| `s` contains only `()[]{}` | No tokenizing/parsing needed. A dict (or `switch`) of 3 pairs is the entire "grammar table." Also: you may **assume the `else` branch is an opener** — no unknown-character policy needed (but state that assumption out loud). |
| `1 <= s.length <= 10^4` | O(n) is trivially fast. O(n²) brute force ≈ 10^8 elementary steps — borderline, and conceptually wrong to present. **Important trap:** a *recursive* validator on a fully nested 10^4-length string exceeds Python's default recursion limit (~1000 frames) — so prefer **iterative** code. |
| "Closed in the **correct order**" | This is the key phrase. It rules out counting solutions and points at *structure* → LIFO. |
| Valid strings are always **even-length** | Every character is consumed in a matched pair, so `if len(s) % 2: return False` is a sound O(1) shortcut. Optional; be ready to justify it. |

Also note: length 0 isn't in scope per constraints, but if it were, the convention is `true` (vacuously valid) — worth one sentence in the interview.

---

## 3. Brute force: delete adjacent matched pairs until stable

### 3.1 Idea

Repeatedly scan `s` and delete every adjacent valid pair `"()"`, `"[]"`, `"{}"` (simultaneously, non-overlapping). Repeat until a pass changes nothing. Valid strings shrink to `""`; invalid ones get stuck non-empty.

```python
def isValid_bruteforce(s: str) -> bool:
    prev = s
    while True:
        cur = prev.replace("()", "").replace("[]", "").replace("{}", "")
        if cur == prev:          # a full pass changed nothing -> stable
            break
        prev = cur
    return prev == ""
```

### 3.2 Worked traces

**`s = "([])"` → expected `true`** (indices are 0-based positions in the current string):

| Pass | String before | Adjacent pairs found (index, value) | Result |
|---|---|---|---|
| 1 | `([])` | (1,2) = `[]` ✓ delete | `()` |
| 2 | `()` | (0,1) = `()` ✓ delete | `` (empty) |
| 3 | `` | none | stable → **true** |

**`s = "([)]"` → expected `false`:**

| Pass | String before | Adjacent pairs found | Result |
|---|---|---|---|
| 1 | `([)]` | (0,1)=`([` ✗, (1,2)=`[)` ✗, (2,3)=`)]` ✗ | unchanged |
| 2 | `([)]` | stable | non-empty → **false** |

The interleaving case is exactly where this method *correctly* stalls — nothing adjacent ever matches.

### 3.3 Complexity

**Time O(n²), space O(n).** Justification: each *shrinking* pass removes at least one 2-character pair, so there are at most ⌊n/2⌋ shrinking passes (plus one final confirming pass); each pass costs O(current length) to scan and rebuild the string, and lengths are O(n) — giving O(n) per pass × O(n) passes. The bound is tight: a fully nested string like `"((((…))))"` removes exactly one layer per pass, needing exactly n/2 passes.

(Practical note: Python's `str.replace` runs at C speed, so this might even pass at n = 10^4 — but presenting it as *the* solution signals weak structure recognition.)

### 3.4 The tempting middle step that is **wrong**: counters

"Count each bracket type, require all counts to be even/balanced and never go negative" — works for **one** bracket type (e.g., LC 921), but fails for three:

- `"([)]"` has counts `(: 1, ): 1, [: 1, ]: 1` — perfectly balanced — yet is invalid. Counters are **order-blind**; they cannot tell `([])` from `([)]`.
- Formally: the set of properly nested strings is the classic example of a language that is context-free but **not regular** — pumping any long-enough word inside its first half breaks the mirror property — so no finite-state machine (including any fixed number of counters) can recognize it. Unbounded stack memory is essential, not incidental.

## 4. The core insight

> **At the moment any closer arrives, the opener it must match is exactly the most recently opened opener that is still unclosed.**

Last opened, **first** closed → LIFO → **stack**. This reduces the whole problem to three explicit checks:

| Failure mode | Example | Detected by |
|---|---|---|
| Closer with nothing open | `")("`, `"]"` | stack empty when a closer arrives |
| Wrong type | `"(]"`, `"([)]"` | popped opener ≠ required partner |
| Opener never closed | `"(("`, `"()("` | stack non-empty after the scan |

Everything else is valid. One left-to-right pass, decide at the **first** violation (early exit).

---

## 5. Optimal approach: one-pass stack

### 5.1 Algorithm

1. Build `closer_to_opener = {')': '(', ']': '[', '}': '{'}`.
2. Scan `s` left to right with index `i` (0-based):
   - If `s[i]` is an **opener** → push it.
   - If `s[i]` is a **closer** → the stack must be non-empty (else fail #1) and `pop()` must equal `closer_to_opener[s[i]]` (else fail #2).
3. After the scan: stack must be empty (else fail #3). Return accordingly.

The stack stores **values** (opener characters), never indices — nothing here needs revisiting.

### 5.2 Python implementation

```python
def isValid(s: str) -> bool:
    closer_to_opener = {')': '(', ']': '[', '}': '{'}
    stack = []                                   # holds opener characters, bottom -> top
    for ch in s:                                 # ch is the VALUE at index i; we don't need i
        if ch in closer_to_opener:               # dict `in` checks KEYS -> true iff ch is a closer
            # short-circuit: `not stack` is checked BEFORE pop(), so no pop on empty
            if not stack or stack.pop() != closer_to_opener[ch]:
                return False
        else:                                    # opener (safe: input is only the 6 brackets)
            stack.append(ch)
    return not stack                             # fail #3: leftover openers
```

**Cleaner variant — push the *expected closer* instead**, so the comparison at close time is a direct equality with no second dict lookup:

```python
def isValid(s: str) -> bool:
    open_to_close = {'(': ')', '[': ']', '{': '}'}
    need = []                                    # stack of required closers, in LIFO order
    for ch in s:
        if ch in open_to_close:                  # opener: register an obligation
            need.append(open_to_close[ch])
        elif not need or need.pop() != ch:       # closer must be exactly the next obligation
            return False
    return not need
```

Optional O(1) pre-check (justify it out loud): `if len(s) % 2: return False`.

### 5.3 Traces of the official examples

All indices are 0-based; the stack column shows character **values**, bottom → top. Dict used: `pairs = {')': '(', ']': '[', '}': '{'}`.

**Example 1 — `s = "()"` → true**

| i | s[i] | action | stack after |
|---|---|---|---|
| 0 | `(` | opener → push | `['(']` |
| 1 | `)` | closer → pop `'('`, matches `pairs[')']` ✓ | `[]` |

End: empty → **true** ✓

**Example 2 — `s = "()[]{}"` → true**

| i | s[i] | action | stack after |
|---|---|---|---|
| 0 | `(` | push | `['(']` |
| 1 | `)` | pop `'('` ✓ | `[]` |
| 2 | `[` | push | `['[']` |
| 3 | `]` | pop `'['` ✓ | `[]` |
| 4 | `{` | push | `['{']` |
| 5 | `}` | pop `'{'` ✓ | `[]` |

**true** ✓

**Example 3 — `s = "(]"` → false**

| i | s[i] | action | stack after |
|---|---|---|---|
| 0 | `(` | push | `['(']` |
| 1 | `]` | closer → pop `'('`, but `pairs[']'] = '['` → **mismatch** | — |

Return **false** at i = 1 ✓

**Example 4 — `s = "([])"` → true** (the nesting case)

| i | s[i] | action | stack after |
|---|---|---|---|
| 0 | `(` | push | `['(']` |
| 1 | `[` | push | `['(', '[']` |
| 2 | `]` | pop `'['`, matches `pairs[']'] = '['` ✓ | `['(']` |
| 3 | `)` | pop `'('`, matches `pairs[')'] = '('` ✓ | `[]` |

**true** ✓ — note the inner `[` sat *on top of* `(` and was resolved first, which is the entire point.

**Example 5 — `s = "([)]"` → false** (the interleaving case)

| i | s[i] | action | stack after |
|---|---|---|---|
| 0 | `(` | push | `['(']` |
| 1 | `[` | push | `['(', '[']` |
| 2 | `)` | closer → pop `'['`, but `pairs[')'] = '('` → **mismatch** | — |

Return **false** at i = 2 (s[3] is never even read) ✓ — a counter would have passed this string; the stack's LIFO order catches it.

### 5.4 Complexity table

| Approach | Time | Extra space | Correct? |
|---|---|---|---|
| Repeated adjacent-pair deletion | O(n²) — ≤ n/2 passes × O(n) each | O(n) rebuilt strings | ✓ (too slow in spirit) |
| Per-type counters | O(n) | O(1) | ✗ order-blind (`"([)]"`) |
| **One-pass stack** | **O(n)** — each character pushed/popped at most once | **O(n)** worst case (all openers) | ✓ |
| Recursion (grammar-style) | O(n) | O(n) call stack | ✓ but risks RecursionError in Python |

**Lower bounds, briefly justified:**

- **Ω(n) time is forced:** every character must be examined in the worst case, because inputs differing at a single position can have different verdicts — e.g., an algorithm that skips the last character can't distinguish `"()"` (true) from `"(]"` (false). So the stack solution is time-optimal.
- **Ω(n) worst-case space is forced** (for any single-pass algorithm on read-only input): there are 3^k distinct length-k prefixes made only of openers, and each can be completed into either a valid string (its mirror) or an invalid one (one wrong closer at the end) — so the algorithm must remember *which* openers are pending, requiring Θ(k) state. Deep nesting is what forces the memory; O(1) space is possible only for a **single** bracket type (counter).

## 6. Indices vs values, duplicates, and edge semantics (precision notes)

- **Values, not indices.** The stack stores opener *characters* because we never revisit positions. Variants that ask you to *repair or report positions* (LC 32 Longest Valid Parentheses, LC 1249 Minimum Remove) push **indices** instead — decide deliberately which one you push, and say so.
- **Indices in traces** are 0-based positions in `s`; `s[i]` is the value at index `i`. Failure records like "false at i = 2" mean the loop returned before reading later indices.
- **Duplicates need no special handling.** Repeated identical characters behave naturally: `"(("` stacks three identical openers that must unwind in exact reverse via `")))"`, and `"()()"` is just consecutive flush-then-empty cycles. Never deduplicate; each character is processed independently.
- **Empty string:** out of scope (n ≥ 1), but the code returns `not stack == True` → `true` for `""`, which is the conventional answer if the constraint were relaxed.
- **Single character:** `"("` → false (leftover), `")"` → false (empty-stack pop) — both fall out of the three checks; no special-casing.

## 8. Common mistakes

### 8.1 Logic bugs

1. **No empty-stack guard before `pop()`** → crash on `")("`. In Python it's an `IndexError`; in Java a `NoSuchElementException`; in C++ it's **undefined behavior**, not an exception. The short-circuit `if not stack or stack.pop() != ...` fixes it in one line.
2. **Forgetting `return not stack`** — returning `true` once all closers matched misses `"(("` and `"()("`. Rule: every closer matched ≠ valid.
3. **Counters instead of a stack** — passes all balance checks, fails `"([)]"`.
4. **Returning `true` mid-scan** on some "balanced so far" condition; validity is a whole-string property.
5. **Adding the odd-length shortcut but presenting it as the algorithm** — it's a pre-filter, not a decision procedure.

### 8.2 Language gotchas

| Language | Gotcha |
|---|---|
| **Python** | `ch in closer_to_opener` tests **keys only** (`values` require `ch in dict.values()`). If you build the dict the other way (`'(' → ')'`) but keep testing keys, openers/closers silently flip. Also: use list `append`/`pop` (O(1) amortized) — never `insert(0, x)` / `pop(0)` (O(n) each). |
| **Java** | Use `Deque<Character> st = new ArrayDeque<>();`, not legacy `java.util.Stack` (synchronized `Vector` subclass, different method names like `empty()`). `pop()` on an empty `Deque` throws `NoSuchElementException`. Compare boxed characters with `.equals()` — `==` happens to work for these ASCII brackets only because of the `Character` cache for 0–127, which is exactly the kind of accident that breaks later. |
| **C++** | `top()`/`pop()` on an empty `std::stack` is **UB** — check `st.empty()` first; and `pop()` returns `void`, so read `top()` before popping. Build the `std::unordered_map<char,char>` (or write a `switch`) **once, outside the loop** — reconstructing it per character is a classic perf slip. |

## 9. Interview script (full talk track)

**Phase 1 — Restate & clarify (~30s).**
"So the input is a string containing only the six bracket characters, length at least one, and I return `true` exactly when every bracket closes properly: same type, correctly nested, nothing dangling in either direction. I'll assume the six-character guarantee holds; and if an empty string were allowed, I'd return `true` for it since nothing can violate."

**Phase 2 — Naive idea, dismissed fast (~15s).**
"Brute force: repeatedly delete adjacent pairs like `()` and `[]` until stable — valid strings empty out, `([)]` gets stuck. That's O(n²): nested inputs need n/2 passes of O(n) each. Worth knowing, not the answer."

**Phase 3 — The insight (~20s).**
"The real observation: when a closing bracket arrives, the only thing it can legally match is the most recently opened, still-unclosed bracket. Last opened, first closed — that's a stack."

**Phase 4 — Algorithm (~30s).**
"One pass. Openers get pushed. On a closer there are exactly two local failures — empty stack, or the popped opener is the wrong type — and one global failure: openers left over at the end. None of the three → valid. Early exit on the first violation."

**Phase 5 — Complexity, with justification (~20s).**
"O(n) time — each character is pushed and popped at most once. O(n) worst-case space, and that's not laziness: a prefix of k openers has 3^k possibilities and can end valid or invalid, so any one-pass algorithm must remember which openers are pending. Counters genuinely cannot work — that's what `([)]` proves."

**Phase 6 — Code + dry run.**
Narrate while typing; then trace `"([])"` (valid, stack grows and unwinds) and `"([)]"` (mismatch at i = 2) line by line.

**Phase 7 — Tests.**
"`(`, `)`, `()( `, and the official five. Also the 10^4 fully-nested string to confirm I'm iterative, not recursive."

## 10. Transferable patterns & related problems

**Pattern: "Resolve the most recent pending obligation" (LIFO matching stack).** Whenever items arrive that must be matched against the *latest unresolved* prior item — brackets, path segments, operators, decode frames — a stack is the tool. Variants:

- Push **values** (this problem) vs push **indices** (when you must edit/report positions).
- Stack holds **partial results** (scores, built strings) rather than pending items.
- **Monotonic stacks** are the same "most recent unresolved" idea with an ordering invariant.

| LC 32 Longest Valid Parentheses | stack of **indices** + sentinel; hardest sibling |

| LC 678 Valid Parenthesis String | adds wildcard `*` — greedy range of possible depths |

| LC 71 Simplify Path | stack of path segments |
| LC 224 / 227 Basic Calculator | bracket stack + expression state |
| LC 1111 Maximum Nesting Depth | depth-only → a counter is enough |

## 11. Say it in 60 seconds

> "Valid parentheses is a stack problem. The reason: when I hit a closing bracket, the only thing it can legally match is the most recently opened, still-unclosed bracket — last opened, first closed, which is LIFO. So I do one left-to-right pass. Openers get pushed. On a closer, exactly two things can fail locally: the stack is empty — a closer with nothing open, like in `)(` — or the popped opener is the wrong type, which is what kills the interleaving case `([)]`. And one global failure: openers left over at the end, like `((`. If none of those three happens, it's valid. One pass, O(n) time; O(n) worst-case space, and that's unavoidable — a prefix of k openers has 3^k possibilities and can finish valid or invalid, so you must remember what's pending, which is also why plain counters fail. Then I'd code it iteratively — a fully nested 10^4 string would blow Python's recursion limit — and test `(`, `)`, `()( `, and `([)]`."
