# 3Sum — Complete Interview Lesson

## 1. The Problem, Restated in Your Own Words

> Given an array `nums` of `n ≥ 3` integers, return **every distinct value-triplet** `(a, b, c)` such that three **different indices** hold `a, b, c` and `a + b + c = 0`. The output must not contain duplicate triplets. Ordering — of the result list and inside each triplet — does not matter.

Three precision points you should state out loud before coding, because they're where most wrong solutions start:

- **Indices vs. values.** `i != j, i != k, j != k` constrains *indices*, not *values*. `[-1, -1, 2]` is a legal triplet in Example 1 because two *different indices* both hold `-1`. Confusing this with "three distinct values" makes you wrongly exclude valid answers.
- **Dedup is on value-multisets.** If twenty different index combinations produce the multiset `{-1, 0, 1}`, it appears **once**. The cleanest mental model: enumerate the *set* `{ sorted(a, b, c) : ∃ i < j < k, nums[i] + nums[j] + nums[k] = 0 }`.
- **We return values, not indices.** That means we may reorder the array freely. (If the interviewer variants this to "return the index triplets," you must carry `(value, original_index)` pairs through the sort — worth mentioning as a flag you checked.)

---

## 2. Decoding the Constraints

| Constraint | What it actually tells you |
|---|---|
| `n ≤ 3000` | An **O(n²)** algorithm does ≈ 9×10⁶ operations — instant. Brute force enumerates C(n,3) = n(n−1)(n−2)/6 ≈ **4.5×10⁹** triples at n = 3000 — far too slow under the usual interview budget of ~10⁸ simple operations per second (a rule of thumb, not a guarantee). So: beat cubic. |
| `-10⁵ ≤ nums[i] ≤ 10⁵` | Any 3-element sum has absolute value ≤ 3×10⁵, which fits easily in a 32-bit signed int (limit ≈ 2.1×10⁹). **Overflow is not a concern here** — but say that sentence out loud; it *becomes* a real bug in 4Sum-style variants where |values| can reach 10⁹ and a 4-element sum reaches 4×10⁹. |
| `n ≥ 3` | No empty-input handling required; a cheap guard is still good hygiene. |
| Duplicates exist in the input (Example 1 has two −1s) | Dedup logic is a first-class part of the problem, not an afterthought. |
| Output = values, order-free | Sorting is allowed (see §1); we can also emit triplets in any internal order, which lets the algorithm produce them pre-sorted for free. |

## 3. Baseline: Brute Force, with a Worked Trace

Enumerate all index triples `i < j < k`, keep zero-sum ones, and dedup by canonicalizing each hit (sort its values, store as a tuple in a set — Python lists are unhashable).

```python
def threeSum_bruteforce(nums: list[int]) -> list[list[int]]:
    n = len(nums)
    seen: set[tuple[int, ...]] = set()          # canonical (sorted) triplets
    for i in range(n):
        for j in range(i + 1, n):
            for k in range(j + 1, n):
                if nums[i] + nums[j] + nums[k] == 0:
                    seen.add(tuple(sorted((nums[i], nums[j], nums[k]))))
    return [list(t) for t in seen]
```

**Worked trace on Example 1** — `nums = [-1, 0, 1, 2, -1, -4]`. There are C(6,3) = 20 index triples; the full sweep:

| 0,1,5 | −1, 0, −4 | −5 | — |

**Takeaways from the trace:** only 3 of 20 triples hit zero, and two of them are the *same value-triplet* from *different index choices* — that's exactly the dedup problem. **Complexity:** O(n³) time, O(u) extra space for the dedup set (u = number of unique triplets). Correct, but ~4.5×10⁹ combos at n = 3000 means minutes in Python and tens of seconds even in fast languages → TLE. It still earns its keep as the *correctness oracle* for the optimized version.

## 4. The Core Insights

1. **"Return values, not indices" ⇒ sorting is free.** Once sorted, equal values sit adjacent, so every dedup decision becomes a *local* comparison with a neighbor.
2. **Sorted array ⇒ 2Sum becomes a two-pointer sweep.** For a fixed first element `nums[i]`, finding `(j, k)` with `nums[j] + nums[k] = −nums[i]` in a sorted suffix takes O(n) time and O(1) space: if the sum is too small, the only fix is a bigger left value; too big, a smaller right value.
3. **So: 3Sum = n instances of sorted-2Sum.** Fix an *anchor* `nums[i]`, two-pointer the window `i+1 … n−1`. Total O(n²).
4. **Dedup by construction, not by a set:** process each *anchor value* once, and after each hit jump both pointers past equal values. No canonical-set needed at all.
5. **Monotone pruning:** if `nums[i] > 0`, every later anchor is also positive, so no zero-sum remains — break early.

## 5. Optimal Approach: Sort + Two Pointers

### 5.1 Algorithm

1. Sort `nums`.
2. For each anchor index `i` from `0` to `n−3` (it needs two elements after it):
   - **Skip** if `i > 0` and `nums[i] == nums[i−1]` (this anchor value was fully processed).
   - **Break** if `nums[i] > 0` (smallest remaining value is positive → no zero sums left).
3. Two pointers `lo = i+1`, `hi = n−1`; loop while `lo < hi`:
   - `s = nums[i] + nums[lo] + nums[hi]`
   - `s < 0` → `lo += 1`; `s > 0` → `hi -= 1`
   - `s == 0` → record `[nums[i], nums[lo], nums[hi]]`; then `lo += 1`, `hi -= 1`, and **skip duplicates**: advance `lo` while `nums[lo] == nums[lo-1]`, pull `hi` back while `nums[hi] == nums[hi+1]` — both guarded by `lo < hi`.

A subtle point people trip on: **skipping duplicate anchors does not lose triplets that use two copies of the anchor value.** For `[-1, -1, 2]`, the anchor is the *first* −1, and the second −1 is still inside the two-pointer window — `lo` may legitimately point at a value equal to the anchor's.

### 5.2 Reference Code (Python)

```python
def threeSum(nums: list[int]) -> list[list[int]]:
    nums.sort()                # use nums = sorted(nums) if the input must not be mutated
    n = len(nums)
    res: list[list[int]] = []

    for i in range(n - 2):                     # anchor needs >= 2 elements after it
        if i > 0 and nums[i] == nums[i - 1]:   # skip duplicate anchor VALUES
            continue
        if nums[i] > 0:                        # sorted: everything after is > 0 too
            break

        lo, hi = i + 1, n - 1
        while lo < hi:
            s = nums[i] + nums[lo] + nums[hi]
            if s < 0:
                lo += 1
            elif s > 0:
                hi -= 1
            else:
                res.append([nums[i], nums[lo], nums[hi]])
                lo += 1
                hi -= 1
                while lo < hi and nums[lo] == nums[lo - 1]:   # skip dup left values
                    lo += 1
                while lo < hi and nums[hi] == nums[hi + 1]:   # skip dup right values
                    hi -= 1
    return res
```

(An equally common style skips *before* moving — `while lo < hi and nums[lo] == nums[lo+1]: lo += 1`, then a final `lo += 1`. Either works; **pick one and stay consistent**, because mixing them can double-skip.)

### 5.3 Traces on the Official Examples

**Example 1:** `[-1, 0, 1, 2, -1, -4]` → sorted: `[−4, −1, −1, 0, 1, 2]` (indices 0–5).

| anchor i | anchor value | lo, hi | (a, lo-val, hi-val) | s | action |
|---|---|---|---|---|---|
| 0 | −4 | 1, 5 | (−4, −1, 2) | −3 | <0 → lo=2 |
| 0 | −4 | 2, 5 | (−4, −1, 2) | −3 | <0 → lo=3 |
| 0 | −4 | 3, 5 | (−4, 0, 2) | −2 | <0 → lo=4 |
| 0 | −4 | 4, 5 | (−4, 1, 2) | −1 | <0 → lo=5 → lo==hi, stop |
| 1 | −1 | 2, 5 | (−1, −1, 2) | **0** | ✅ record [−1,−1,2]; lo=3, hi=4; no dups to skip |
| 1 | −1 | 3, 4 | (−1, 0, 1) | **0** | ✅ record [−1,0,1]; lo=4, hi=3 → stop |
| 2 | −1 | — | — | — | `nums[2] == nums[1]` → skip anchor |
| 3 | 0 | 4, 5 | (0, 1, 2) | 3 | >0 → hi=4 → stop |

Output: `[[-1,-1,2], [-1,0,1]]` ✅ — note the anchor at `i=1` (first −1) produced a triplet whose `lo` value is *also* −1, exactly the subtle case from §5.1.

**Example 2:** `[0, 1, 1]` → sorted `[0, 1, 1]`. i=0: lo=1, hi=2 → s = 0+1+1 = 2 > 0 → `hi=1` → stop. Output `[]` ✅.

**Example 3:** `[0, 0, 0]` → i=0: lo=1, hi=2 → s=0 → record `[0,0,0]`, lo=2, hi=1 → skip loops guarded by `lo < hi` do nothing → stop. `range(n−2) = range(1)` → done. Output `[[0,0,0]]` ✅. (This tiny case is the one that **crashes** implementations whose skip loops lack the `lo < hi` guard — see §8.)

### 5.4 Why Dedup Is Sound and Complete

- **No duplicates (soundness):** each *anchor value* is processed once; within one anchor, after every emission `lo` jumps past all copies of the emitted left value, so successive emissions have *strictly increasing* `nums[lo]` (and strictly decreasing `nums[hi]`). Two emitted triplets can therefore never be equal as multisets.
- **No misses (completeness, exchange argument):** while both members `j < k` of a real zero-sum pair are still inside the `[lo, hi]` window, the current sum is ≤ their sum = 0, so `hi` never jumps left past `k`. When `lo` reaches `j`: either the current sum is negative — then no remaining element pairs with `nums[j]` to reach zero (everything to its left within the window is ≤ current), so dropping `j` is safe — or the sum is zero and `(j, hi)` is recorded. Symmetrically for `hi`.

### 5.5 Optional Prunes (Nice to Mention, Not Required)

```python
if nums[i] + nums[i + 1] + nums[i + 2] > 0: break      # smallest possible sum already > 0
if nums[i] + nums[n - 2] + nums[n - 1] < 0: continue   # largest possible sum still < 0
```

Each preserves correctness by monotonicity: with the anchor fixed, these are the minimum/maximum achievable sums, so a zero is impossible in that direction.

## 6. Variant: If Sorting Is Not Allowed → Hashing

If the interviewer asks for the "can't sort / need original indices" version, fix the anchor and run classic hash-set 2Sum on the suffix:

```python
def threeSum_hash(nums: list[int]) -> list[list[int]]:
    res: set[tuple[int, ...]] = set()
    n = len(nums)
    for i in range(n - 2):
        target = -nums[i]
        seen: set[int] = set()
        for j in range(i + 1, n):
            need = target - nums[j]
            if need in seen:
                res.add(tuple(sorted((nums[i], nums[j], need))))
            seen.add(nums[j])
    return [list(t) for t in res]
```

Notes worth voicing: `seen` only holds values at indices strictly between `i` and `j`, so the two pair-indices are distinct from each other and from `i` — index-distinctness is automatic. Dedup, however, is no longer free: you must canonicalize each hit (sorted tuple) into a set, which is exactly the bookkeeping that sorting made unnecessary. Expected O(n²) time (hash operations are O(1) on average under standard simple-uniform-hashing assumptions; adversarial inputs can degrade them), O(n) extra space.

## 7. Complexity Analysis

| Approach | Time | Extra space (excl. output) | Notes |
|---|---|---|---|
| Brute force + canonical set | O(n³) | O(u), u = # unique triplets | ≈ 4.5×10⁹ combos at n=3000 → TLE |
| **Sort + two pointers (chosen)** | **O(n log n) + O(n²) = O(n²)** | O(1) for the sweep; sort buffer O(n) for Python's Timsort, O(log n) typical for C++ introsort | canonical interview answer |
| Anchor + hash 2-sum | O(n²) expected | O(n) | use when sorting is disallowed |
| Output size itself | — | up to **Θ(n²)** triplets | e.g., positives `1..m` plus negatives `−3, −4, …, −(2m−1)`: every one of the Θ(m²) positive pairs sums to a value whose negation is present, so every pair extends to a zero-sum triplet |

Two context points that impress interviewers, with their justifications:

- **Is O(n²) optimal?** Unproven, but the *3SUM conjecture* — a foundational conjecture of fine-grained complexity, supported by the fact that decades of work have produced only slightly subquadratic algorithms (small polylogarithmic-type improvements in restricted integer settings) — asserts that 3SUM requires n^{2−o(1)} time, so O(n²) is believed essentially worst-case optimal.
- **Sorting cost:** the O(n log n) sort term is asymptotically unavoidable *in the comparison model* only if you must sort — any comparison sort needs Ω(n log n) comparisons because n! orderings exist and each comparison yields at most one bit of information. Since our total is O(n²) anyway, this term is irrelevant here; it only matters in follow-ups where the dominant term changes.

## 8. Common Mistakes

| # | Mistake | Why it breaks | Fix |
|---|---|---|---|
| 1 | Reading "distinct indices" as "distinct values" | Wrongly drops `[-1,-1,2]` | Dedup on value-multisets; indices just need `i<j<k` |
| 2 | Anchor dedup as `nums[i] == nums[i+1]` | On `[-1,-1,2]` it skips the *first* −1, leaving an anchor whose window lacks the second −1 → triplet missed | Skip when `i > 0 and nums[i] == nums[i-1]` (process the *first* occurrence) |
| 3 | Missing the `i > 0` guard on anchor dedup | At `i=0`, Python's `nums[i-1]` is `nums[-1]` — the **last** element (silent wrong answer: `[0,0,0]` fails if the last element equals the first); in C++/Java it's an out-of-bounds read | Always `i > 0 and nums[i] == nums[i-1]` |
| 4 | Not moving **both** pointers after a hit | Duplicates: `[-2,0,0,2,2]` emits `[-2,0,2]` twice; moving *neither* loops forever | `lo += 1; hi -= 1` on every hit |
| 5 | Duplicate-skip loops without the `lo < hi` guard | `[0,0,0]` → `lo` walks to index 3 → `IndexError` in Python; and Python's negative indexing can silently read the wrong slot instead of crashing; in C++ it's UB | Guard every skip loop with `lo < hi` |
| 6 | Deduping unsorted triplets, or putting a `list` in a `set` | Same multiset counted twice; lists are unhashable | Canonicalize with `tuple(sorted(...))` — or dedup structurally as in §5 so no set is needed |
| 7 | Anchor loop bounds: `range(n)`, or C++ `nums.size() - 2` | Usually harmless (empty window), but C++ `size()` is unsigned: `size() - 2` **underflows** if n < 2 when constraints generalize | `range(n - 2)` in Python; in C++ take `int n = nums.size()` and guard `n < 3` |
| 8 | Blanket assumptions about overflow | Here |sum| ≤ 3×10⁵ fits `int32`; in 4Sum variants with |values| ≤ 10⁹ a 4-element sum reaches 4×10⁹ and **does not** | Check magnitude bounds per problem; use 64-bit sums when needed |

## 9. Language Gotchas (Python / Java / C++)

| Language | Gotchas to flag out loud |
|---|---|
| **Python** | Negative indexing (`nums[-1]`) masks off-by-one bugs in dedup comparisons — see mistakes #3/#5. Lists are unhashable → dedup sets need tuples. `nums.sort()` mutates the caller's array; use `nums = sorted(nums)` if mutation is unwanted. |
| **Java** | `Arrays.asList(nums)` on an `int[]` produces a single-element `List<int[]>`, **not** `List<Integer>` — build triplets with `List.of(a, b, c)` or an `ArrayList`. Boxed `Integer` comparison with `==` is only reliable for the −128..127 autobox cache; use `.equals()`/`.intValue()`. `int` sums are fine here, but switch to `long` for large-value variants. |
| **C++** | `nums.size()` is unsigned: `size() - 2` underflows if generalized below n = 2 — store `int n = nums.size();` and guard `n < 3`. Missing `lo < hi` guards cause out-of-bounds reads (UB), not exceptions. Use `long long` for sums in large-value variants. |

## 10. Test Cases to Say Out Loud

Propose the first three **before** coding (they shape the dedup design), verify the rest after:

| Input | Expected | What it exercises |
|---|---|---|
| `[-1,0,1,2,-1,-4]` | `[[-1,-1,2],[-1,0,1]]` | Official Ex. 1 — duplicate anchor values, out-of-order input |
| `[0,1,1]` | `[]` | Official Ex. 2 — no valid triplet |
| `[0,0,0]` | `[[0,0,0]]` | Official Ex. 3 — triplet uses the anchor value at all three roles; kills unguarded skip loops |
| `[0,0,0,0]` | `[[0,0,0]]` | Four zeros — dedup **across** anchors, not just within a sweep |
| `[-2,0,0,2,2]` | `[[-2,0,2]]` | Duplicate `lo` values *and* duplicate `hi` values in one two-pointer sweep (mistake #4) |
| `[1,2,3]` | `[]` | All positive — exercises the `nums[i] > 0 → break` prune |
| `[-100000, 0, 100000]` | `[[-100000, 0, 100000]]` | Extreme magnitudes — confirms int sums are safe here (and prompts the overflow remark) |

Micro-trace worth reciting for `[-2,0,0,2,2]`: anchor −2, `lo=1 (0)`, `hi=4 (2)` → s=0, record `[-2,0,2]`; then the left-skip advances past the second `0` and the window collapses — the duplicate pair `(0, 2)` is never re-tested. That single sentence proves you handle the hardest dedup case.

## 11. Transferable Patterns & Related Problems

**Patterns this problem teaches:**

- **Sort-first for "unique combinations from a multiset":** when the answer is a *set of value-collections*, sorting makes duplicates adjacent and turns global dedup into local neighbor checks. Same trick in Subsets II and Combination Sum II (skip duplicates at the same recursion depth).
- **Sorted pair-search = two pointers:** an exchange argument (move the pointer that can't possibly participate) gives O(n) pair-finding with O(1) space. The general shape: sum too small → advance left; too big → retreat right; on a hit, advance both and skip equals.
- **Reduce k-Sum to 2-Sum:** fix outer elements, recurse. 3Sum = anchor + 2Sum (O(n²)); 4Sum = two anchors + 2Sum (O(n³)); k-Sum = O(n^{k−1}). Dedup discipline applies at *every* level.
- **"Return values, not indices ⇒ sorting allowed"** — a 10-second check to run on any problem statement.

**Related problems to drill next:**

| Problem | Relationship |
|---|---|
| Two Sum (LC 1) | The hash-map base case |
| Two Sum II (LC 167) | The sorted two-pointer base case |
| 3Sum Closest (LC 16) | Same skeleton; track the best |sum − target| instead of equality |
| 3Sum Smaller (LC 259) | Key twist: when `s < target`, **all** `hi − lo` pairs with this `lo` are valid — count them in bulk |
| 4Sum (LC 18) | Two anchors + two pointers; overflow now matters → 64-bit sums |
| 4Sum II (LC 454) | Different shape: counter over A×B pair sums, lookup `−(c+d)` in C×D — O(n²) time/space |

## 12. Full Interview Talk Track

**Understand (first 60 seconds).** "Let me play back the problem: I need every *unique value-triplet* summing to zero. The index constraint is about indices, not values — so `[-1,-1,2]` counts when two indices hold −1. The output is a set of value-triplets, no duplicates, order irrelevant. Since we return values and not indices, sorting the array is fair game — I'll rely on that."

**Brute force and its bound.** "Naively: three nested loops over `i < j < k`, test the sum, and dedup by dropping each hit into a set as a sorted tuple. Correct, but that's C(n,3) ≈ n³/6 ≈ 4.5 billion triples at n = 3000 — way over budget. I'll keep it mentally as the correctness oracle and do better."

**Plan.** "Sort. Then for each anchor index `i`, the subproblem is: find pairs in `nums[i+1 … n−1]` summing to `−nums[i]`. That's 2Sum on a sorted array — two pointers. Sum too small, advance `lo`; too big, retreat `hi`; O(n) per anchor, O(n²) total. Free bonus prune: once the anchor is positive, three positives can't sum to zero, so break."

**Dedup — the crux.** "Sorting makes equal values adjacent, so dedup becomes local: an anchor equal to its predecessor is skipped — I process the *first* occurrence, and later copies are still inside the window, so two-copy triplets like `[-1,-1,2]` are still found. After each hit I move both pointers inward and jump past equal values on each side, guarded by `lo < hi`. That makes dedup structural — no canonical-set needed."

**Complexity.** "O(n log n) sort plus O(n²) sweep; O(1) beyond the sort buffer and the output. The output itself can be Θ(n²) — think positives `1..m` plus negatives `−3..−(2m−1)`, where every positive pair completes to a zero-sum triplet — so quadratic total is unavoidable in the worst case, and the 3SUM conjecture suggests you can't beat ~n² asymptotically anyway."

**Tests.** "The three official examples, plus `[0,0,0,0]` for cross-anchor dedup, `[-2,0,0,2,2]` for pointer-skips on duplicates, an all-positive array for the early break, and an extreme-magnitude case for overflow sanity."

## 13. Say It in 60 Seconds

> "3Sum: return every unique triplet of **values** summing to zero — indices must differ, values may repeat, no duplicate triplets in the output. Brute force is n³-over-6 — dead at n = 3000 — so: sort, fix the smallest element as an anchor, and run two pointers on the remainder for target minus-anchor: sum too low, move left up; too high, move right down; on zero, record and jump both pointers past duplicate values so each triplet emits exactly once. Skip anchors equal to the previous one, and break once the anchor goes positive — three positives can't sum to zero. Sorting is legal because we return values, not indices, and it makes dedup a local neighbor check. Total: O(n log n) sort plus O(n²) sweep, O(1) extra space beyond the sort and output. Tests I'd run: the three official examples, `[0,0,0,0]` for cross-anchor dedup, `[-2,0,0,2,2]` for pointer-skips, and an all-positive array for the early break."

*(~140 words — recitable in under a minute at normal interview pace. If you're cut off at 30 seconds, the minimum viable version is: sort → anchor → two pointers → skip duplicates at the anchor and after each hit → O(n²).)*
